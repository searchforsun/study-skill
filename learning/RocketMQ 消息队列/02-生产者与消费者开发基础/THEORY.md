## 一、生产者三种发送方式：同步、异步与单向

生产者向 Broker 投递消息时，面临一个根本选择：**调用线程要不要等结果？等到什么程度？** RocketMQ 提供了三条路径——同步发送（等 Broker 确认）、异步发送（不等，通过回调拿结果）、单向发送（不关心结果）。三种方式的对比如下：

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | 同步发送（Sync） | 调用线程阻塞等待 Broker 确认；返回 `SendReceipt` 含 `messageId`；可靠性最高 |
| 2 | 异步发送（Async） | 调用线程立即返回，结果通过回调通知；需自行管理回调线程安全与等待逻辑 |
| 3 | 单向发送（Oneway） | 不等待任何响应，不关心是否成功；吞吐最高但消息可能静默丢失 |
| 4 | 发送重试 | 同步/异步失败有内置重试，单向无重试也无声 |

### 同步发送：可靠性的默认答案

**同步发送是可靠性优先的默认选择。** 调用线程进入 send 方法后，客户端完成「序列化 → 网络写 → 等待 Broker 确认 → 解析响应」全链路才返回。返回的 `SendReceipt` 携带 Broker 分配的 `messageId`（全局唯一），调用方据此做后续业务关联（如记录发送日志、对账）。

同步发送的代价是延迟：一次 send 的耗时 = 网络 RTT + Broker 落盘时间 + 序列化开销。在 RocketMQ 5.x 中，默认超时由 `ClientConfiguration` 控制，本地环境通常在毫秒级完成，但跨机房或高负载时会显著增加。因此对于核心业务链路（如支付状态通知），同步发送的等待成本是可以接受的——**丢失一条消息的代价远大于等几毫秒**。

同步发送的关键代码形态（5.x API）：

```java
// 同步发送 — 阻塞直到 Broker 返回确认
SendReceipt receipt = producer.send(message);
// receipt.getMessageId() 可用于业务追踪
```

### 异步发送：高吞吐下的回调模型

**异步发送把「等」的工作从调用线程转移到回调线程。** `send` 调用立即返回，不阻塞业务线程；Broker 确认到达后，回调的 `onSuccess` 或 `onException` 在 Netty/gRPC 的 IO 线程上执行。

这带来两个工程约束：

1. **回调中不能做重操作**：回调在 IO 线程执行，长时间阻塞会拖慢整个客户端的网络处理。若业务需要在发送成功后做 DB 写入或 RPC 调用，应提交到独立线程池。
2. **必须等待回调完成再关闭 Producer**：异步发送的语义是"稍后通知我"，若主线程发完消息立即 `producer.close()`，未完成的回调将被丢弃。标准做法是使用 `CountDownLatch` 或 `CompletableFuture` 汇聚。

异步适用于**高吞吐、对单条延迟不敏感**的场景——例如批量日志上报、埋点数据写入。通过批量聚合异步发送，可以在不阻塞业务线程的前提下充分利用网络带宽。

### 单向发送：不关心结果时的极端选择

**单向发送连响应都不读。** 消息写入 socket 缓冲区后 send 方法立即返回，不等待任何 ACK。这意味着：

- **吞吐最高**：无等待、无回调开销。
- **无声丢失**：网络断开、Broker 拒绝、Topic 不存在——调用方完全不知道。日志类、非关键的监控上报可以考虑；任何涉及业务状态的场景都不应使用。

在 RocketMQ 5.x gRPC 客户端中，单向发送并非独立 API，而是通过不读取 `SendReceipt` 的方式模拟（或使用 `sendAsync` 忽略回调）。4.x Remoting 客户端提供了独立的 `sendOneway` 方法。

### 三种方式的决策框架

| 场景 | 推荐方式 | 理由 |
|------|---------|------|
| 订单状态通知、支付回调 | 同步 | 必须确认消息已落盘才能继续业务流程 |
| 日志聚合、埋点上报（大量） | 异步 | 吞吐优先，少量丢失可接受 |
| 非关键监控心跳 | 单向 | 丢了无影响，吞吐最大化 |
| 需要发送后立即获取 messageId | 同步 | 异步回调中拿 ID 时序上靠后 |

## 二、消息结构与属性：不止是 Payload

消息是 RocketMQ 中唯一的通信载体。初看一条消息只是 `body`（字节数组），但 RocketMQ 在 body 之外附加了**元数据层**——路由用的 Tag、追踪用的 Key、扩展用的用户属性——它们共同决定了消息的**路由路径、过滤方式和可观测性**。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | Topic | 消息的逻辑分类，决定路由到哪个 Broker 的哪些队列 |
| 2 | Tag | Topic 内的二级分类，用于消费者过滤（减少拉取无关消息） |
| 3 | Key | 业务唯一标识（如订单 ID），用于消息追踪与幂等去重 |
| 4 | 用户属性（User Properties） | 键值对元数据，可参与 SQL92 过滤（阶段 3） |
| 5 | 消息体（Body） | 业务载荷，建议用 JSON/Protobuf 序列化 |

### Topic：第一层路由决策

**Topic 是消息的顶层命名空间，决定消息被路由到哪组队列。** 生产者在 send 时指定 Topic，Broker 根据 Topic 配置的队列数量（默认 8 个写队列，可配置）将消息写入对应的 CommitLog。消费者通过订阅 `Topic + 过滤表达式` 声明自己感兴趣的消息范围。

Topic 命名没有强约束，但实践中建议用分层命名：`业务域.子域.动作`（例如 `order.pay.notify`），避免使用下划线或其他可能导致 URL 编码歧义的特殊字符。一个应用尽量使用一个 Topic，消息子类型用 Tag 区分——这避免了创建大量 Topic 带来的元数据膨胀和管理成本。

### Tag：生产者标记，消费者过滤

**Tag 是 Topic 内的二级标签，让消费者无需拉取全部消息就能过滤出感兴趣的子集。** 生产者发送消息时附加一个 Tag 字符串（如 `"PAID"`、`"CANCELLED"`），消费者订阅时指定 `TagA || TagB` 表达式——Broker 在推送/拉取前按 Tag 过滤，减少了网络传输和消费者端的无效反序列化。

Tag 的过滤发生在 Broker 端（而不是消费者端），这是性能上的关键保障。但 Tag 不适合承载高基数值（如用户 ID）——此时应使用自定义属性和后续阶段介绍的 SQL92 过滤。

### Key：消息级别的身份证

**Key 是业务层的消息唯一标识，不与路由或过滤耦合。** 典型用法是填入业务主键（如订单号 `ORD-20260510-001`）。Key 有两个核心价值：

1. **消息追踪**：在 RocketMQ Dashboard 或命令行工具中按 Key 查询，可定位一条消息的完整生命周期（何时发送、被谁消费、消费耗时）。
2. **幂等去重**：消费端通过 Key 做业务去重（在 DB 或缓存中记录已处理的 Key），应对至少一次投递带来的重复消费。

5.x API 中通过 `setKeys()` 设置，支持多个 Key（逗号分隔）。**每条消息都应设置 Key**——它是排障时最重要的索引字段，没有之一。

### 用户属性与消息体

**用户属性是键值对形式的扩展元数据**（`setProperty("region", "east")`），可在 SQL92 过滤中使用（阶段 3 深入）。消息体建议用 JSON（可读性好、调试方便）或 Protobuf（体积小、跨语言强），避免 Java 原生序列化（版本耦合严重）。

## 三、PushConsumer 与 SimpleConsumer：两种消费心智模型

RocketMQ 5.x 提供了两种主流的消费者接口：**PushConsumer**（推模型，监听器回调）和 **SimpleConsumer**（拉模型，主动 receive + ack）。它们在并发模型、灵活性、ACK 责任上的差异直接决定了业务代码的写法。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | PushConsumer | SDK 管理拉取循环，业务只需实现 `MessageListener`，返回 SUCCESS 即 ACK |
| 2 | SimpleConsumer | 业务主动 `receive()`，处理完显式 `ack()`；灵活但责任更大 |
| 3 | 消费并发模型 | PushConsumer 内置线程池；SimpleConsumer 业务自行管理并发 |
| 4 | ACK 与重试 | PushConsumer 返回 RECONSUME_LATER 触发重试；SimpleConsumer 不 ACK 则超时重投 |

### PushConsumer：封装程度最高，适合标准业务

**PushConsumer 将「拉取—投递—确认」封装为不可见的循环**：SDK 在后台持续从 Broker 拉取消息，拆分成单条（或小批量）投递给注册的 `MessageListener`。监听器返回 `ConsumeResult.SUCCESS` 等效于 ACK，Broker 推进消费偏移；返回 `ConsumeResult.FAILURE` 则触发重试。

这种封装的好处是**业务代码简洁**：你只需关心"收到一条消息后做什么"，不必关心如何拉取、如何管理偏移。代价是**灵活性受限**——拉取速率、批量大小、偏移管理都由 SDK 自动决策，无法按业务特点微调。

PushConsumer 的监听器回调在 SDK 管理的线程池中执行。5.x gRPC 客户端默认线程数较小（与 CPU 核数相关），若业务逻辑较重，须确保回调不长时间阻塞，否则会拖慢同一连接上的其他消费。

### SimpleConsumer：原子接口，适合精细控制

**SimpleConsumer 把拉取和确认拆成两个原子操作**，业务方拿到主动权，也承担相应责任：

1. `receive(maxMessages, invisibleDuration)` — 批量拉取最多 N 条消息，同时设置**不可见时间**（在此期间消息不会被其他消费者实例拿到）。
2. `ack(messageView)` — 处理成功后显式确认。
3. 若在不可见时间内未 ACK，消息自动重新可见，被再次投递——等效于自动重试。
4. 可以在处理过程中调用 `changeInvisibleDuration()` 延长处理窗口。

这种设计适用于**需要精细化流量控制**的场景：比如消费速率受下游限流、需要按业务优先级批量处理、或需要在 ACK 前做复杂的多步事务。但代价也很明显——你必须管理好 `receive` 循环的线程模型、`invisibleDuration` 的取值（太短触发无效重试，太长阻塞队列消费）、以及异常路径下的补偿。

### 消费并发模型

**PushConsumer 的并发由 SDK 内部线程池管理**：长轮询连接数、消费线程数都由 `ClientConfiguration` 中的参数控制。对于大部分业务，默认配置足以应对；若发现消费堆积，优先检查业务逻辑耗时而非调大线程数——更大的线程池可能把下游压垮。

**SimpleConsumer 的并发完全由业务方决定**：你可以起多个线程各自 `receive`，或使用单线程 + 异步处理。这种自由度的正确用法是：先压测下游系统的承载上限，再反推消费并发度——而不是盲目加线程。

### 如何选择

- 标准业务场景（收到消息 → 处理 → 记录结果）→ **PushConsumer**，代码量最小。
- 需要控制消费速率、批量聚合、或复杂 ACK 策略 → **SimpleConsumer**。
- PullConsumer（4.x 遗留 API）仅推荐在流处理框架（如 Flink Connector）中使用，一般业务不应直接使用。

## 四、消费者组与负载均衡：为什么同组内消息不重复投递

如果一个 Topic 有 8 个队列，一个消费组有 3 个消费者实例——消息如何分配？为什么同一条消息不会同时被组内两个实例拿到？答案在于**消费者组（ConsumerGroup）的负载均衡机制**。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | ConsumerGroup | 逻辑上的消费集群；同组内消息分摊，跨组独立消费 |
| 2 | 队列分配 | 按队列粒度分配消费者；消费者数 > 队列数时多余消费者空闲 |
| 3 | 负载均衡触发 | 消费者上线/下线、队列数变化时重分配；有短暂不可用窗口 |
| 4 | 至少一次投递 | 正常路径不丢消息，但重平衡等边界可能触发重复 |

### ConsumerGroup：消费的隔离单元

**ConsumerGroup 是消息消费的隔离边界。** 同一个 Topic 可以被多个 ConsumerGroup 独立订阅——每个 Group 各自维护消费偏移（offset），各自消费全量消息。这实现了「一条消息被多个下游系统各自独立处理」的发布-订阅模式。

例如：Topic `order.pay` 的消息，ConsumerGroup `inventory` 负责扣库存，ConsumerGroup `notification` 负责发通知——两个 Group 各自消费所有订单支付消息，互不干扰。**但同一个 Group 内，一条消息只投递到一个消费者实例**——这是负载均衡的核心语义。

### 队列粒度的分配

**RocketMQ 的负载均衡以队列（MessageQueue）为粒度，而不是以消息为粒度。** Broker 在写入消息时，将消息按轮询（或指定选择策略）分配到 Topic 的多个队列中。消费者上线时，通过 Rebalance 算法将队列分配给同 Group 的各实例——每个实例拿到一组队列的消费权。

这导致一个硬约束：**消费者实例数超过队列数时，多余的实例处于空闲**。例如一个 Topic 有 8 个队列，10 个消费者实例——只有 8 个在工作，2 个闲置。这是设计选择而非 Bug：以队列为分配粒度避免了消息级别的锁竞争，但也意味着队列数是并行消费的上限。

### 负载均衡的触发时机

Rebalance 在以下事件触发：

1. 消费者实例上线（加入 Group）。
2. 消费者实例下线（进程退出、网络断开、心跳超时）。
3. Broker 上该 Topic 的队列数发生变化。

每次 Rebalance 期间，消费者会短暂暂停消费，重新计算队列归属，然后恢复。这意味着**频繁的消费者上下线会导致消费间断和可能的重复消费**（本实例处理到一半的消息被重新分配给新实例，旧实例的未确认消息被新实例再次投递）。生产实践中应避免消费实例频繁重启——这是至少一次语义下重复消息的主要来源之一。

### 至少一次投递与业务幂等

**RocketMQ 保证至少一次投递（at-least-once），不保证恰好一次（exactly-once）。** 正常消费路径中，一条消息只会被投递一次并确认成功。但在以下边界场景可能重复：

- Rebalance 过程中未确认的消息被重新分配。
- 消费者 ACK 网络超时但 Broker 实际已处理——消费者重试导致重复消费。
- Broker 主从切换时 offset 回退。

因此**业务方必须设计幂等**：以消息 Key 为主键去重，或利用数据库唯一约束天然拒绝重复写入——这是从「消息中间件的投递语义」到「业务正确性的最终防线」。

## 五、集群消费与广播消费：两种分发模式的选择

同一消费组内，消息如何分发到各实例？答案取决于**消费消息模型**的设置：**集群消费（CLUSTERING）**和**广播消费（BROADCASTING）**。它们决定了一条消息是被组内一个实例消费，还是被所有实例消费。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | 集群消费（CLUSTERING，默认） | 每条消息只被组内一个消费者处理；消息分摊、支持负载均衡 |
| 2 | 广播消费（BROADCASTING） | 每条消息被组内所有消费者处理；无负载均衡、偏移存本地 |
| 3 | 广播的限制 | 不支持顺序消息、不支持重置消费位点、偏移不持久化到 Broker |

### 集群消费：分摊负载的默认模式

**集群消费模式下，一条消息在同一个 ConsumerGroup 内只投递一次**——由 Rebalance 结果决定哪个实例获得该消息所在队列的消费权。这是 RocketMQ 的默认模式，适用于绝大多数业务场景：多个消费者实例共同分摊消息处理负载，实例越多、处理能力越强（但受队列数上限约束）。

消费偏移存储在 Broker 端，消费者重启后能从上次位置继续消费。控制台可查看消费进度、重置位点——这些运维能力都依赖 Broker 端的偏移存储。

### 广播消费：每个人都收到一模一样的消息

**广播消费模式下，同 Group 的每个消费者实例各自消费全量消息**——相当于每个实例都有一份独立的消息副本。消费偏移存储在消费者本地文件系统（`LocalFileOffsetStore`），不依赖 Broker。这意味着：

- 每个实例的消费进度完全独立，A 的进度不影响 B。
- 重启消费者后偏移从本地文件恢复，若文件丢失则回到最早或最晚位置（取决于配置）。
- Dashboard 无法查看广播模式下的消费进度——因为没有上报到 Broker。

广播消费适用于**每个实例都需要相同事件通知**的场景：例如所有应用节点都需要刷新本地缓存、所有微服务实例都要收到配置变更通知。但受限也明显：不支持顺序消息、不支持位点重置、消费者增减不会触发 Rebalance。

### 5.x gRPC 客户端中的广播消费

在 `rocketmq-client-java`（5.x 新客户端）中，广播消费的配置方式与 4.x 有所不同。5.x 的 `PushConsumer` 通过 `SubscriptionExpression` 的配置间接控制；部分云厂商的 5.x 实例可能已废弃广播模式，需要为每个消费者创建独立订阅组来模拟广播效果。具体以你使用的 Broker 版本和客户端版本为准——务必在动手前查阅对应的兼容性说明。

### 场景选择

| 场景 | 推荐模式 | 理由 |
|------|---------|------|
| 订单处理、用户积分计算 | 集群消费 | 消息不能重复处理，需负载均衡 |
| 本地缓存刷新、配置热更新 | 广播消费 | 每个节点都需要收到变更通知 |
| 监控告警通知 | 广播消费 | 每个监控处理器独立判断是否触发 |
| 日志聚合（多个下游入库） | 多个 ConsumerGroup（集群模式） | 更灵活，各组独立管理偏移和重试 |
