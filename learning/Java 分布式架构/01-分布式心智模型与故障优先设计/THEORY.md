## 一、分布式系统本质：从「确定」到「概率」

### 1.1 为什么分布式系统不可忽略不确定性

单机系统的核心假设是：**操作原子性 + 执行结果确定 + 故障罕见**。一旦进程跨越网络边界，这三条全部打破——消息会丢、重试会重复、节点会宕机、时钟会漂移。分布式架构师的首要心智转变是：从「命令式执行」（发请求→等响应→完成）切换到「概率式推理」（发请求→超时判断→决定下一步）。

**这条认知切换比学会任何中间件 API 更根本。**

### 1.2 故障模型三分法

**崩溃故障（Crash Failure）**：节点停止回应，视为宕机。处理手段是超时探测 + 候选节点切换。

**遗漏故障（Omission Failure）**：节点对请求既不响应也不记录，相当于「石沉大海」。网络丢包、GC 停顿时都呈现这种行为。超时是唯一外部可见信号，无法区分「节点挂了」「节点太慢」还是「网络断了」。

**拜占庭故障（Byzantine Failure）**：节点返回错误或恶意响应。互联网后端多数场景默认不处理此类故障；跨信任域或特定金融场景才需要抵抗拜占庭。**本路线默认非拜占庭假设**，这是工程成本与风险的核心折中。

> 理解故障分类才能正确设置超时阈值。实践中若将遗漏故障当崩溃故障处理（过早切换节点），会产生「双主」竞争；若将崩溃故障当遗漏故障处理（无限重试），会放大雪崩。

## 二、CAP 定理：工程含义而非学术表述

### 2.1 一致性三级别

**强一致性（Linearizability）**：所有读写操作在全局时间线上顺序排列，读操作总是看到最近一次写的结果。实现代价：同步复制（多数派写入），延迟高，节点故障时不可用。典型场景：分布式锁、账号余额、库存扣减。

**顺序一致性（Sequential Consistency）**：操作满足各节点视角的时间顺序，但不要求全局真实时钟一致。比线性一致性弱，但通常足够且性能更好。

**最终一致性（Eventual Consistency）**：允许短暂不一致窗口，但保证在没有新写入时最终收敛。代价最低，但应用层必须处理「读到过期数据」。典型场景：用户画像、社交点赞、推荐列表。

### 2.2 CAP 选择是业务决策，不是技术洁癖

| 业务场景 | 推荐一致性级别 | 理由 |
|----------|----------------|------|
| 支付/账户/库存 | 强一致 | 资损不可逆 |
| 社交Feed/评论 | 最终一致 | 用户对延迟的容忍远高于对一致性 |
| 配置/路由/白名单 | 顺序一致或强一致 | 错误路由影响面大 |

**工程要点**：不要因为「业界说 CAP 三选二」就认为最终一致是低级方案；也不要因「我们用了分布式数据库」就默认强一致。选择应在架构文档中显式声明，并附上「不一致窗口最大可接受时长」这一业务指标。

### 2.3 一致性级别与延迟/可用性的关系

**强一致 → 低延迟 trade-off**：线性一致性要求同步复制，多节点写入需要多数派确认，延迟必然高于异步复制。在跨机房或跨地域场景下，强一致的延迟可能高达数百毫秒。

**可用性 vs 一致性的实务判断**：当业务能接受「账户扣款后短暂看到余额未扣减」（如电商营销活动），最终一致是合理选择；当业务是支付/金融，一致性窗口可能导致资损，强一致不可妥协。

## 三、超时与重试：组织默认值的起点

### 3.1 超时判断的本质是概率决策

设置超时不是查表，而是回答：「我愿意为这次调用等待多久？超过这个时间后，调用方应该做什么？」

- 超时过短 → 频繁误判节点故障，流量被打散，资源消耗放大
- 超时过长 → 故障节点上的请求堆积，雪崩风险上升

**实践原则**：按依赖服务的 SLO 设置超时，例如依赖服务 P99 延迟是 50ms，则超时至少设为 2× P99 = 100ms 起步，加上网络波动余量。

### 3.2 重试的边界与风暴防御

**重试三原则**：

1. **只在读操作或有明确幂等性的写操作上重试**。支付回调、库存扣减等非幂等操作一旦重试可能导致资损。
2. **重试次数上限 + 指数退避 + jitter**。固定间隔重试会在故障时形成同步震荡；无 jitter 的指数退避会在恢复瞬间形成流量尖峰。
3. **重试链路须有熔断保护**。当下游错误率超过阈值（如 50%），停止重试直接降级，防止雪崩。

### 3.3 指数退避与Jitter的工程价值

**无退避的问题**：固定间隔重试会在故障恢复瞬间形成流量尖峰（想象 1000 个客户端同时在 1s 后重试）。

**指数退避**：每次重试间隔 ×2，如 100ms → 200ms → 400ms。

**Jitter（抖动）**：在指数退避基础上加随机偏移（如 ±20%），打散重试峰值。

```java
// 指数退避 + jitter 示例
long baseDelay = (long) Math.pow(2, attempt - 1) * 100;
long jitter = (long) (Math.random() * baseDelay * 0.2);
long delay = baseDelay + jitter;
Thread.sleep(delay);
```

## 四、Java 并发最小必要集：本地幻觉的根源

### 4.1 线程与内存模型（JMM）

Java 内存模型规定了「主内存」与「工作内存」的划分：线程对共享变量的读写不一定立刻同步到主内存，可能在 CPU 缓存中暂挂。这导致：

```java
// 线程 A
flag = true;          // 写通知主内存
count = 1;           // 写通知主内存

// 线程 B（可能在另一核）
if (flag) {          // 读取 flag 可能仍是 false
    // 看不到 count 的更新
}
```

**这是「本地幻觉」的根源：单线程内代码顺序与多线程实际执行顺序无关。**

### 4.2 可见性与三个等价陷阱

| 场景 | 本地幻觉 | 正确认知 |
|------|----------|----------|
| 缓存 map 缓存热点数据 | 认为读线程一定看到新值 | volatile 或锁保证可见性 |
| CompletableFuture 异步回调 | 认为主线程一定在回调完成后才继续 | 必须 get() 或 join() 阻塞等待 |
| 双检查锁定单例 | 认为初始化完成前其他线程一定看不到 | 必须用 volatile 禁止指令重排 |

### 4.3 竞态条件与临界区

竞态 = 多个线程对共享变量的读写顺序不确定。防御手段：

- **不可变对象**：无竞态（推荐）
- ** synchronized / Lock**：序列化访问（简单粗暴，慎用大段）
- **原子变量（AtomicInteger 等）**：无锁化，适合计数器场
- **Copy-on-Write**：读多写少场景

### 4.4 分布式与本地并发的本质区别

| 维度 | 本地并发 | 分布式并发 |
|------|----------|------------|
| 故障假设 | 可忽略 | 必须假设 |
| 时钟 | 共享，精确 | 独立，有漂移 |
| 可见性 | 共享内存 | 网络延迟 |
| 回滚手段 | 事务/锁 | 幂等 + 补偿 |
| 失败成本 | 内存不一致 | 可能是数据不一致或资损 |

**核心结论：本地幻觉的本质是将单机并发的「确定性直觉」应用于分布式环境——时钟不同步、故障假设不同、回滚手段不同，这些差异导致同样的代码模式在分布式环境下产生完全不同的故障行为。**

## 五、分布式锁：高频事故点的系统性认知

### 5.1 为什么分布式锁是「高发事故点」

锁的本质是「在某一时刻只允许一个持有者访问共享资源」。在单机这是低成本的协调；在分布式环境中，锁依托于外部存储系统，而存储系统本身也可能故障或发生网络分区。此时锁的持有者可能：

- 持有锁的进程崩溃，但锁未及时释放（TTL 设计缺陷）
- 主从切换导致锁语义漂移（Redis 主从场景）
- 释放时校验不足，误删他人锁

### 5.2 Redis 分布式锁的典型错误

**错误一：TTL 设置不当**。若进程持有锁后长时间 GC 或 pause，锁已自动释放，但业务尚未完成。此时另一个进程获得同一把锁，两个进程同时操作共享资源。解决方案：锁的 TTL 应大于业务最大执行时间；更保险的是引入「续约」机制。

**错误二：释放时未校验持有者**。释放锁只是 `DEL key`，不验证调用者是否是锁的持有者。后果是：进程 A 的锁过期，进程 B 获得锁，进程 A 从 GC 恢复后执行 `DEL`，把进程 B 的锁删了。正确做法是 `Lua` 脚本原子校验并删除。

**错误三：主从切换下的锁丢失**。在 Redis 主从架构中，若主节点在锁同步到从节点之前宕机，从节点晋升为主节点，但锁数据丢失。此时另一个进程可获得同一把锁。Redlock 方案试图解决此问题，但其代价与争议须在具体场景中权衡。

### 5.3 ZooKeeper / etcd 类锁的适用边界

ZK/etcd 基于一致性协议（ZAB/Raft），提供强一致的有序锁。其优势在于：锁语义不会因网络分区而漂移，支持 WATCH 机制实现公平锁。但代价是：运维复杂度高，事务延迟高于 Redis。

**适用场景**：跨信任域的关键互斥、需要严格公平性的场景。

**若业务可用「幂等 + 队列串行」替代，则分布式锁往往是过度设计。**

### 5.4 数据库锁：何时更简单可靠

- **乐观锁（版本号/ CAS）**：适合读多写少、冲突概率低的场景。不阻塞，失败则重试。
- **悲观锁（SELECT FOR UPDATE）**：适合写冲突频繁的场景。会阻塞其他事务，但语义清晰。
- **唯一约束**：适合防重复提交场景（如幂等键）。数据库保证唯一性，最简单。

### 5.5 分布式锁的选用决策

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|----------|
| Redis SETNX + TTL | 弱一致（有丢失风险） | 高 | 低 | 非关键互斥 |
| Redlock | 弱一致 | 高 | 高 | 高要求互斥（慎用） |
| ZK/etcd 锁 | 强一致 | 中 | 高 | 关键互斥 |
| 数据库唯一约束 | 强一致 | 低 | 低 | 防重复提交 |

**核心原则：分布式锁是最后手段——优先幂等、串行化热点、领域不变式、队列单消费者。**
