## 一、韧性工程的本质：假设故障，然后防御

### 1.1 什么是韧性（Resilience）

韧性不是「不出故障」，而是在故障发生时**系统能继续提供服务（或优雅降级）**。核心思想是：**默认所有外部依赖都不可靠**，在此基础上设计防御手段。

### 1.2 韧性工程与可靠性的区别

| 维度 | 可靠性（Reliability） | 韧性（Resilience） |
|------|----------------------|---------------------|
| 目标 | 消除故障 | 限制故障影响范围 |
| 手段 | 预防为主 | 假设故障，接受故障，容错 |
| 关注点 | 系统整体 | 局部故障的扩散控制 |
| 成本 | 高（冗余、测试、流程） | 中（降级、熔断、重试） |

### 1.3 故障扩散的典型路径

1. **单点故障**：服务 A 依赖服务 B，B 宕机导致 A 也宕机
2. **雪崩**：A 重试 B，B 更慢，更多重试，更慢，最终 A 也不可用
3. **级联故障**：A → B → C → D，故障沿调用链向上扩散

**防御原则**：在每个调用节点设置「停止条件」，防止故障无限扩散。

## 二、超时链设计：层级与保守原则

### 2.1 为什么要分层超时

一次请求可能经过：网关 → 负载均衡器 → 服务 A → 服务 B → 数据库。每一跳都可能超时。若全局使用同一个超时（如 3000ms），则无法区分「哪一跳慢」，也难以针对性处理。

**超时链设计原则**：
1. 每跳超时应小于上一跳的剩余时间
2. 下游超时设上限，上游超时设下限
3. 按依赖服务的 SLO 动态调整

### 2.2 超时配置的保守原则

| 配置项 | 建议公式 | 说明 |
|--------|----------|------|
| 单次调用超时 | P99 × 2 + 网络波动 | 避免误判 |
| 重试次数 | ≤ 3 | 防止重试风暴 |
| 总超时预算 | 响应时间 SLO × 系数 | 留给重试和降级的空间 |

**反模式**：超时配置抄默认值（如 3000ms 一刀切），既无业务含义也无法应对突发流量。

### 2.3 超时与故障类型的关系

超时只能感知「该到的没到」，但无法区分：
- 节点崩溃（崩溃故障）
- 节点太慢（GC pause 或高负载）
- 网络断开（遗漏故障）

**设计启示**：超时阈值应大于 P99 + 一定余量，避免把正常慢查询误判为节点故障。

## 三、重试策略：有边界的 retry

### 3.1 重试的三原则

1. **幂等性优先**：只有读操作或明确幂等的写操作才能重试。支付、库存扣减等非幂等操作一旦重试可能造成资损。
2. **上限 + 退避**：重试次数上限（如 3 次）+ 指数退避 + jitter，防止同步震荡。
3. **熔断兜底**：当下游错误率超过阈值（如 50%），停止重试直接降级。

### 3.2 指数退避与 Jitter

**无退避的问题**：固定间隔重试会在故障恢复瞬间形成流量尖峰（想象 1000 个客户端同时在 1s 后重试）。

**指数退避**：每次重试间隔 ×2，如 100ms → 200ms → 400ms。

**Jitter（抖动）**：在指数退避基础上加随机偏移（如 ±20%），打散重试峰值。

```java
// 指数退避 + jitter 示例
long baseDelay = (long) Math.pow(2, attempt - 1) * 100; // 100, 200, 400, 800...
long jitter = (long) (Math.random() * baseDelay * 0.2);   // ±20%
long delay = baseDelay + jitter;
Thread.sleep(delay);
```

### 3.3 重试风暴的防御

**问题**：下游故障恢复时，大量积压请求同时重试，可能再次压垮下游。

**防御手段**：
- 熔断器在恢复后「半开」状态，逐步释放流量而非瞬间恢复
- 请求入口处使用令牌桶/限流，防止突发重试
- 重试队列有上限，超限直接拒绝

### 3.4 幂等性判断

| 操作类型 | 能否重试 | 原因 |
|----------|----------|------|
| GET（读） | ✓ | 幂等，只读不写 |
| DELETE（删除） | ✓ | 幂等，重复删除效果相同 |
| POST（创建） | ✗ | 非幂等，重复创建产生重复数据 |
| PUT（更新） | 视情况 | 业务幂等（如幂等键去重）可重试 |
| 支付回调 | ✗ | 非幂等，重试可能导致重复支付 |

## 四、熔断器：故障时的快速失败

### 4.1 熔断器三状态

| 状态 | 条件 | 行为 |
|------|------|------|
| **Closed（关闭）** | 正常调用，失败率 < 阈值 | 调用正常通过，计数器记录失败 |
| **Open（打开）** | 失败率 > 阈值（如 50%） | 所有调用快速失败，不发往下游 |
| **Half-Open（半开）** | Open 一段时间后 | 放行一个请求试探，成功则转 Closed，失败则继续 Open |

### 4.2 熔断参数的业务含义

熔断器参数（失败率阈值、窗口时间、恢复试探间隔）不是技术常量，而是**业务语义**：

- 失败率阈值 50%：下游已经不可靠到影响自身可用性，必须降级
- 窗口时间 10s：统计周期不宜过短（抖动大），也不宜过长（反应慢）
- 半开试探数 3：恢复时逐步放量，避免瞬间打垮下游

### 4.3 熔断与降级的关系

熔断是**触发条件**，降级是**处理手段**。熔断后必须有明确的降级方案（返回缓存、默认值、功能简化），否则熔断只是让用户看到错误而非降级后的可用结果。

**常见降级策略**：
- 返回缓存数据（读请求）
- 返回默认值（如空列表、0）
- 功能简化（如推荐算法切到规则引擎）
- 进入排队队列（异步处理）

### 4.4 熔断恢复的「半开」机制

熔断恢复时若瞬间放行全部流量，可能再次压垮下游。半开状态逐步放量：

1. 放行一个请求试探
2. 成功 → 逐步增加流量（25% → 50% → 100%）
3. 失败 → 重新打开熔断器

## 五、舱壁模式：隔离与保护

### 5.1 什么是舱壁（Bulkhead）

舱壁原本是船舶设计中的隔舱：船体破损时，水不会蔓延到全船。在软件中，舱壁是**资源隔离**的手段，防止某个组件耗尽全部资源影响其他组件。

### 5.2 舱壁的实现方式

| 类型 | 说明 | 示例 |
|------|------|------|
| **线程池隔离** | 不同调用链使用独立线程池 | 商品服务线程池 50，订单服务线程池 30 |
| **信号量隔离** | 限制并发数而非线程数 | 限制对下游的并发调用数 |
| **连接池隔离** | 数据库/消息队列连接池分离 | 不同服务使用独立的 DB 连接池 |

### 5.3 舱壁与熔断的配合

舱壁防止资源耗尽，熔断防止故障扩散。典型配合：

1. **线程池隔离**：商品查询用独立线程池，即使订单查询把线程池打满，商品查询仍可响应
2. **熔断兜底**：线程池耗尽时，熔断器打开，快速失败而非排队等待

### 5.4 舱壁的代价

舱壁不是免费的：独立线程池意味着更多线程、更多内存占用、更复杂的监控。需要权衡：
- 高价值核心路径 → 独立线程池保护
- 低价值辅助路径 → 共享线程池即可

## 六、限流与降级：保护系统不被冲垮

### 6.1 限流的层级

| 层级 | 说明 | 典型实现 |
|------|------|----------|
| **入口限流** | 网关/API Gateway 层面 | Nginx、Sentinel API Gateway |
| **服务间限流** | 服务调用时 | Sentinel、 Resilience4j |
| **资源限流** | DB/连接池层面 | 连接池大小、SQL 超时 |

### 6.2 限流算法

| 算法 | 原理 | 适用场景 | 缺点 |
|------|------|----------|------|
| **令牌桶** | 按固定速率发放令牌，请求消耗令牌 | 平滑突发流量 | 实现稍复杂 |
| **滑动窗口** | 统计时间窗口内的请求数 | 精确限流 | 占用内存 |
| **漏桶** | 请求以固定速率出桶 | 整流限速 | 无法处理突发 |
| **固定窗口** | 每时间窗口允许 N 个请求 | 简单场景 | 有边界突刺 |

### 6.3 降级与业务语义的对齐

降级不是技术手段，而是**业务决策**。限流降级必须与业务方提前约定：

1. **降级顺序**：核心业务 > 核心功能 > 辅助功能
2. **降级后的用户体验**：展示什么内容，是否提示用户
3. **降级期间的数据补偿**：如缓存数据、异步处理

**反模式**：降级预案与技术实现脱节（业务说可接受降级，技术发现降级后整个页面不可用）。

## 七、Sentinel 与 Dubbo 治理语义

### 7.1 Sentinel 核心概念

| 概念 | 说明 | 对应治理语义 |
|------|------|-------------|
| **Resource** | 被保护的资源（接口、方法） | 保护什么 |
| **Rule** | 限流/熔断/降级规则 | 怎么保护 |
| **Slot Chain** | 处理槽链（限流→熔断→降级→统计） | 处理顺序 |
| **Cluster Mode** | 集群流控 | 跨实例协调 |

### 7.2 Sentinel 与本地限流的区别

本地限流（如 Resilience4j）只能保护单实例，无法应对集群维度的流量压力。Sentinel 集群模式通过 Token Server 协调各实例的限流决策，保证集群总 QPS 不超限。

### 7.3 Dubbo 的超时与重试治理

Dubbo 默认重试 2 次（总共 3 次调用），默认超时 1000ms。这些默认值在生产环境可能不合适：

- 超时过短：误判率高，调用被打散
- 重试非幂等操作：可能造成重复扣款

**最佳实践**：在注册中心或配置文件统一管理超时/重试参数，按业务场景分类（快速失败场景 vs 容忍延迟场景）。

## 八、RPC vs REST：演进与运维的 trade-off

### 8.1 对比矩阵

| 维度 | RPC（Dubbo/gRPC） | REST（HTTP/JSON） |
|------|-------------------|------------------|
| 性能 | 高（二进制协议、连接复用） | 中（JSON 解析开销） |
| 语言中立性 | 强（IDL 生成客户端） | 强（任何语言 HTTP 即可） |
| 可调试性 | 弱（二进制难以抓包） | 强（明文 JSON，可直接浏览器测试） |
| 版本兼容性 | 弱（IDL 变更影响双方） | 强（字段新增不影响旧消费者） |
| 生态集成 | 强（SkyWalking 等 APM 深度集成） | 中（一般 APM 够用） |

### 8.2 选型建议

**选 RPC**：高性能场景、内部服务调用、已有 Dubbo/SOA 体系。

**选 REST**：对外开放 API、跨语言场景、需要快速迭代。

**核心原则**：技术选型应匹配**组织成熟度与演进需求**，而非追新。
