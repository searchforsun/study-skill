## 一、战略 DDD：子域与限界上下文

### 1.1 为什么传统拆分方式行不通

按表拆分、按功能拆分、先买 MQ 再画边界——这些方式的共同问题是：**以技术视角而非业务视角切割系统**。结果是：

- 服务间调用链过于紧密，形成「分布式单体」
- 跨服务的业务逻辑散落在各服务，修改时牵一发动全身
- 数据库被多个服务直接访问，耦合难以演进

### 1.2 子域分类

每个业务域（Domain）可划分为：

| 子域类型 | 说明 | 例子 |
|----------|------|------|
| **核心域（Core Domain）** | 业务竞争力所在，须重点投入 | 电商中的订单履约 |
| **支撑域（Supporting Subdomain）** | 须实现但非核心竞争力 | 库存管理 |
| **通用域（Generic Subdomain）** | 可采购方案解决 | 邮件通知、SSO |

**资源有限时，优先投入核心域。**

### 1.3 限界上下文与上下文映射

限界上下文是**业务边界的技术声明**。每个上下文有自己的：

- **领域模型**（领域对象、聚合、领域服务）
- **通用语言**（术语含义可能跨上下文不同，如「用户」在账户上下文 vs 交易上下文中含义不同）
- **团队自主权**（独立部署、独立技术栈）

**上下文映射（Context Mapping）** 描述上下文之间的关系：

| 映射类型 | 说明 | 何时用 |
|----------|------|----------|
| **共享内核（Shared Kernel）** | 两个上下文共享部分模型 | 紧密协作的两个团队，须控制共享边界 |
| **客户-供应商（Customer-Supplier）** | 上游提供接口，下游消费 | 独立团队，独立演进 |
| **防腐层（ACL）** | 在本上下文内转换外部模型 | 集成遗留系统或不受控的外部服务 |
| **开放主机服务（OHS）** | 对外暴露协议，按需调用 | 须对外开放 API 的场景 |
| **跟随者（Conformist）** | 直接依赖上游模型 | 上游稳定，团队无影响力 |

## 二、战术 DDD：聚合、聚合根与一致性边界

### 2.1 聚合的设计原则

聚合是**数据一致性边界**：聚合内的对象共同保证业务不变式，聚合之间通过 ID 引用而非直接访问对方内部状态。

**设计原则**：

1. 聚合应尽量小，避免大聚合导致并发冲突
2. 聚合根（Aggregate Root）是唯一对外暴露的入口
3. 跨聚合的协作通过**领域事件**而非直接调用

### 2.2 聚合根的职责

聚合根负责：
- 维护聚合内的业务不变式
- 控制对聚合内对象的访问（外部只能通过聚合根操作）
- 发布领域事件（跨聚合协作的触发点）

### 2.3 聚合与事务边界对齐

这是 DDD 与分布式数据一致性的关键连接点：

- **单聚合内**：事务一致性，由聚合根保证
- **跨聚合**：最终一致性，通过领域事件异步同步

**反模式**：跨聚合大事务（试图在多个聚合间保持强一致）。正确做法是**接受最终一致**，用补偿逻辑处理不一致。

- **核心概念**：聚合作为数据一致性边界、聚合根作为唯一入口、维护聚合内业务不变式、跨聚合最终一致（事件驱动）、聚合与事务边界对齐
- **拓展提问提示词**

## 三、领域事件：跨聚合协作的事实载体

### 3.1 领域事件的本质

领域事件是**业务领域中发生的重要事件**，代表「已经发生的事实」。设计良好的领域事件：

- **命名用过去式**（OrderPlaced、PaymentConfirmed）
- **包含足够重建状态的信息**（事件内容即事实本身）
- **不可变**（历史事件不能修改）

### 3.2 跨聚合协作示例

订单聚合在 `OrderPlaced` 事件后，库存聚合订阅该事件执行库存扣减。两者通过事件解耦，无需跨聚合事务：

```
订单聚合                    事件总线                    库存聚合
  |                            |                         |
  |-- 创建订单 --------------->|                         |
  |                            |                         |
  |                            |-- OrderPlaced -------->|
  |                            |                         |-- 扣减库存
```

### 3.3 领域事件与消息队列的区别

| 维度 | 领域事件 | 消息队列 |
|------|----------|----------|
| 语义 | 「已发生的事实」 | 任务/指令 |
| 命名 | 过去式（OrderPlaced） | 祈使句（扣减库存） |
| 内容 | 事实本身（足够重建状态） | 操作指令（可能需额外查询） |
| 用途 | 跨聚合状态同步 | 异步任务、削峰 |

---

**本节提要（延伸学习）**

- **核心概念**：领域事件定义（已发生的事实）、命名规范（过去式）、不可变、内容自包含（足够重建状态）、跨聚合最终一致性协作、领域事件与消息队列的语义区别
- **拓展提问提示词**

## 四、契约与 API 版本策略

### 4.1 契约的重要性

服务间契约一旦发布就成为约束。修改契约（增删字段、改变语义）会影响所有消费者。若无版本策略，契约漂移会导致系统不可预测。

### 4.2 兼容策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| **顺序兼容（Backward Compatible）** | 新版本兼容旧版本消费者 | 字段只能新增，不能删除或改类型 |
| **向后不兼容（Breaking Change）** | 必须升级所有消费者 | 重大重构，但须有迁移窗口 |
| **双向协议（Dual Protocol）** | 新旧版本同时运行 | 大版本过渡期 |

### 4.3 API 版本管理实践

1. **显式版本**：`/api/v1`、`/api/v2`
2. **演进策略**：先向后兼容，积累不兼容变化后升版
3. **契约测试**：消费者驱动契约测试（CDC）验证兼容性
4. **文档**：OpenAPI/Swagger 文档化，版本变更记录

---

**本节提要（延伸学习）**

- **核心概念**：契约作为服务间约束、顺序兼容（新字段可新增）/破坏性变更（必升级）、显式版本管理（/v1/v2）、消费者驱动契约测试（CDC）、OpenAPI 文档化
- **拓展提问提示词**

## 五、演进路径与反模式

### 5.1 何时拆分，何时合并

**拆分的驱动因素**：
- 业务边界清晰，团队自主演进需求高
- 不同一致性级别或技术栈需求
- 独立部署、独立扩展的需求

**合并的驱动因素**：
- 团队规模小，协作成本高
- 服务间调用过于紧密（分布式单体特征）
- 数据一致性要求高，跨服务事务难以避免

### 5.2 反模式警示

| 反模式 | 特征 | 应对 |
|--------|------|------|
| 按表拆服务 | 每次查表就调一次服务 | 重审限界上下文，按业务能力而非数据模型拆分 |
| 分布式单体 | 服务拆开了但调用链没变短 | 减少同步调用，引入异步事件 |
| 纳米服务 | 一个服务只包含一个类 | 合并，按聚合或模块组织 |
| 先买 MQ 再切业务 | 技术驱动而非业务驱动 | 回到 DDD，按业务边界演进 |

### 5.3 演进路径：Strangler Fig 与双写

**Strangler Fig（绞杀者模式）**：新功能在新服务实现，老功能逐步迁移，最终下掉老实现。适用于遗留系统演进。

**双写过渡**：新老系统同时写入，数据逐步迁移。风险是双写期间数据可能不一致，须有对账机制。
