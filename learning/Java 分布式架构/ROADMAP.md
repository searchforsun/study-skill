## 本路线定位

| 取向 | 说明 |
|------|------|

| **强化** | **架构师决策**：在约束下给出 **可辩护结论**（备选方案、否决理由、残余风险）；**故障优先** 默认假设网络与进程不可靠；**DDD 工程落地**（限界上下文→契约→演进）；**国内互联网典型实践**（流量、营销、交易、内容等场景的模式映射）。 |

## 领域概述（紧凑版）

多进程协作下交付 **可伸缩、可容错、可演进** 的系统；形态含微服务/模块化单体、消息与事件、云原生编排及缓存/DB/搜索组合。**DDD** 用于对齐 **限界上下文与组织边界**，避免「按表拆服务」「先买中间件再切业务」；本路线将 **战略/战术 DDD** 与 **分布式模式** 绑在一起讲，不单列空洞方法论。

### 国内互联网常见技术栈（参照帧 · 非学习目标）

**典型组合**：Java 17/21 LTS + Spring Boot 3 +（Spring Cloud Alibaba **或** Dubbo 3 + **Nacos**）+ **RocketMQ** + **Sentinel** +（**Seata** 按需）+ **SkyWalking** + **K8s**（ACK/TKE/CCE 等）+ Prometheus/Grafana。**等价映射**：同一能力域可用别的成熟实现替代；讨论始终以 **语义与模式** 为准。

| 能力域 | 国内高频参照 | 架构决策要点（非 API） |
|--------|----------------|------------------------|
| 注册/配置/RPC | Nacos、Dubbo、Spring Cloud Alibaba | 契约与耦合：RPC vs REST；注册中心的 **可用性/一致性** 对配置漂移的影响 |
| 流量治理 | Sentinel、网关 | 限流 **维度**（入口/服务间/MQ）；熔断与 **业务降级预案** 是否一致 |
| 消息 | RocketMQ、Kafka（常见） | **投递语义**、顺序与热点分区、幂等与 DLQ 策略 |
| 分布式事务 | Seata 等 | 与 Saga/本地消息表/Outbox 的 **代价对比**；忌「一站式迷信」 |
| 数据 | MySQL、Redis、（PolarDB/TiDB/OceanBase 等按团队） | 分片倾斜、缓存一致性级别、热点 |
| 可观测 | SkyWalking、Prometheus、云 APM | Trace 与日志关联；SLO 与 **告警噪声** |
| 交付 | K8s、镜像仓、CI/CD | 探针、优雅下线；密钥与审计语境下的最小权限 |

## 学习原则（四条）

1. **先决策前提**：业务约束 → **一致性/延迟/成本** → 再谈组件；每个结论写清 **trade-off 与反模式**。  
2. **故障优先**：默认 **超时、部分失败、重复、乱序**；设计先回答「坏了会怎样、范围多大、怎么观测与回滚」。  
3. **DDD 与工程一体**：**限界上下文 / 聚合 / 领域事件** 先成立，再映射注册中心、MQ、事务模式。  
4. **`demo/` 印证语义**：验证故障是否被遏制、语义是否符合假设；**不**替代官方教程。

## 通用工程场景与对策（精炼）

> 各阶段结合国内参照栈讨论 **模式与约束**，**不**绑定具体命令。  

| 场景簇 | 典型诱因 | 对策方向（选型须声明业务语义） |
|--------|-----------|--------------------------------|
| **部分失败与超时链** | hanging、级联、同步链过长 | 超时层级；舱壁；依赖分级；缩短同步半径 |
| **重试与幂等** | 重试风暴、重复投递、客户端重试 | 上限+jitter；仅在安全层重试；幂等键/版本/语义 |
| **缓存与一致性** | 穿透/击穿/雪崩、短暂不一致 | Cache-aside 与 TTL 策略；接受 **最终一致** 的显式声明 |
| **热点与倾斜** | 分片/分区打爆 | 分键与热点隔离；队列削峰；租户隔离 |
| **事务与跨聚合协作** | 强一致冲动 vs 复杂度 | 忌滥用全局 2PC；Saga/TCC/本地消息表/Outbox；补偿模型对齐领域 |
| **顺序与因果** | 乱序、时钟不可靠 | 分区顺序键；单写者；幂等+版本；忌 wall clock 仲裁关键路径 |
| **集群与运维类（运行时/发布）** | 脑裂、错配、发布混杂、毒消息 | Quorum 交给基础设施；金丝雀与 Kill switch；DLQ 与隔离消费池 |
| **集群与运维类（配置中心）** | 全集群 **配置漂移**、**配置推送风暴** | **配置分级**；**本地缓存兜底**；**灰度推送**；**配置回滚机制** |
| **跨团队协作** | 契约漂移 | API 版本与兼容矩阵；**上下文映射（ACL/OHS）** 与契约评审 |

## 国内互联网典型领域场景（精炼）

> 与上表 **叠加**：同一业务往往同时命中「限流、缓存、消息、事务」。**先 DDD 划界，再选工程手段。**

| 场景 | 压力特征 | 对策方向 |
|------|-----------|----------|
| **大促/秒杀/尖峰** | 极高 QPS、库存与超卖 | 订购/库存/营销 **边界**；业务化削峰（预约、分桶等）；全链路压测与容量预算 |
| **营销补贴/券/裂变** | 资损、灰产 | 促销/风控 **子域**；规则与画像边界；幂等与对账 |
| **交易·支付·清算** | 一致性与渠道差异 | 账户/支付/渠道 **上下文**；最终一致+对账为主；忌跨上下文「大事务」 |
| **订单履约长链路** | 多系统状态、逆向 | 聚合不变式 vs **Saga/领域事件**；状态机显式；补偿可见 |
| **内容/直播/推荐** | 读多写少、热点延迟 | 内容与交易 **解耦**；多级缓存；按场景声明一致性级别 |
| **会员/积分/成长** | 规则多变 | 稳定领域接口；账务类变更可追溯；忌规则散落 |
| **通知/触达** | 海量、重复、延时 | 通知 **独立上下文**；投递语义与幂等；活动隔离 |
| **多活/单元化（按需）** | 归属与延迟 | 用户/租户与单元绑定；跨单元忌强同步；RPO/RTO 前置共识 |
| **灰度/演练/合规** | 版本并存、审计 | 发布契约与开关治理；影子流量；数据分级与审计字段 |
| **数据集成与数仓对接** | 一致性、实时性、吞吐量权衡 | **领域事件** 作为数据出口；**CDC** 与 **Outbox**；数据质量、血缘与对账口径 |

## 各阶段详情（模式 · trade-off · 反模式）

### 阶段 1：分布式心智模型与故障优先设计

- **决策焦点**：在何种业务下接受哪种 **一致性级别**；超时与重试的 **组织默认值** 草案。  
- **主题**：CAP **实务**；线性/顺序/最终一致；不确定性与超时；Java 并发 **最小必要集**（线程池、CompletableFuture、共享状态陷阱——**本地幻觉**）。  
- **小段落 · 分布式系统故障模型**：补齐故障分类直觉——**崩溃故障**（节点宕机、进程死掉）；**遗漏故障**（丢包、超时、hang，等价于「该到的没到」）；**拜占庭故障**（任意错误甚至恶意行为）。多数互联网后端默认 **非拜占庭**；特定场景（如跨信任域、部分链路基座）才强化假设。与后续的 **超时、重试、幂等、校验和隔离** 可直接对照。  
- **专题 · 分布式锁的陷阱**：分布式锁是 **高发事故点**，易与「单机锁直觉」混淆；需单独辨析 **trade-off**，而非背 Redis 命令。  
  - **Redis 典型错误**：过期时间设置不当、**误删他人锁**（释放校验）、主从切换下的 **锁语义漂移**（与 Redlock 等方案的争议与适用边界——撰写时以权威文档为准）。  
  - **ZooKeeper / etcd 类锁**：强一致协调 **适用边界**（会话、惊群、运维复杂度）；何时优于「业务幂等 + 队列串行」。  
  - **数据库锁**：何时 **乐观锁/悲观锁/唯一约束** 更简单可靠；与业务事务边界的配合。  
  - **原则**：**分布式锁往往是最后手段**——优先 **幂等、串行化热点、领域不变式、队列单消费者**；锁放大故障面且难观测。  
- **反模式**：把单机锁/事务幻觉搬到分布式；无上限重试；**为抢锁而抢锁**（未回答「为何不能幂等/串行」）。  
- **实践**：部分失败序列图；小型并发 demo（竞态/可见性）；可选桌面推演「锁丢了会发生什么」。  
- **阅读**：撰写 `THEORY.md` 时检索 Java SE、DDIA（概念章）；Redis/ZK **语义与设计** 章节（非命令大全）。

### 阶段 2：DDD·限界上下文·契约与演进式架构

- **决策焦点**：拆分/不拆分的 **论据**；上下文边界与团队对齐；同步 vs 事件的 **耦合代价**。  
- **主题**：战略（子域、限界上下文、映射）+ 战术（聚合、不变式、领域事件）；微服务 **对应关系**；API 版本与兼容。  
- **反模式**：按表拆服务、贫血模型、分布式单体、纳米服务、先买 MQ 再画边界。  
- **实践**：事件风暴或等价产出；最小链路验证 **破坏性变更影响面**。  
- **阅读**：DDD 原著/实现类参考书；Spring/Nacos/Dubbo **概念文档**（非 API 大全）。

### 阶段 3：韧性工程与典型交互故障

- **决策焦点**：限流 **放在哪一层**；降级 **业务预案** 与领域边界是否一致。  
- **主题**：超时链；重试+jitter；熔断/舱壁；Sentinel 等映射 **治理语义**；RPC vs REST **演进与运维** trade-off。  
- **反模式**：重试风暴；同步链过长；熔断参数抄默认值无业务含义。  
- **实践**：故障注入对比；韧性 **默认策略清单**；可选大促推演。  
- **阅读**：Sentinel、Dubbo 集群/超时 **语义**；Resilience4j（若团队栈如此）。

### 阶段 4：数据侧经典场景与一致性模式

- **决策焦点**：每个场景声明 **一致性与资损窗口**；事务模式 **否决理由** 书面化。  
- **主题**：缓存模式与三大问题；分片倾斜；**读写分离与主从延迟**——读一致性级别与 **业务语义** 匹配；主从延迟的 **可观测**（复制位点/延迟指标）与应对（读路由、强制读主、异步补偿）；2PC/TCC/Saga/Outbox/本地消息表 **边界**；消息语义与 **跨聚合** 协作；聚合 vs 事务边界。  
- **专题 · 分库分表的反模式**：扩展手段 **坑多**，宜 **决策清单** 而非一味拆分。  
  - **分键错误** → **分片倾斜**、热点不可迁移；与领域边界不对齐导致「分布式单体数据库」。  
  - **跨库 join / 全局排序** → 与应用层聚合成本、**分布式事务** 诱惑（往往应改模型或读写分离+冗余）。  
  - **扩容难题**：再均衡窗口、双写/校验、路由切换；**过早分库** 的运维税。  
  - **何时不该分**：数据量与团队运维尚未触及痛点；可用 **垂直拆分、归档、冷热分层** 先行。  
- **反模式**：跨聚合大事务；用分布式事务掩盖烂边界；默认可线性读却走从库导致 **隐性不一致**；**为分库而分库**（无明确分键与演进预案）。  
- **实践**：同一业务故事 **两种模式** 对比残余风险。  
- **阅读**：MySQL/Redis/MQ **语义与设计**；Seata **模式限制**（按需）。

### 阶段 5：可观测、容量与稳定性治理

- **决策焦点**：**错误预算** 烧完后优先砍谁（功能/依赖/流量）。  
- **主题**：日志关联、黄金信号、Tracing；压测解读（P99、饱和度）；限流降级与 SLO。  
- **专题 · 告警治理（降噪与可信）**：稳定性常见短板是 **告警噪声** 而非缺告警。  
  - **阈值与错误预算挂钩**：按 **SLO/错误预算消耗速率** 设触发条件，避免「CPU>80% 就喊」。  
  - **分级与升级**：P1/P2 与值班响应；升级路径（超时未_ack、联动值班经理），避免人人 @channel。  
  - **降噪手段**：聚合/抑制（同源折叠）、**维护窗口**、动态基线、依赖降噪（上游已告警则下游抑制）。  
  - **避免「狼来了」**：定期 **告警盘点**；误报必修；以 **可行动性** 为准入（收到告警能否下一步操作）。  
- **反模式**：指标全红无法行动；无容量曲线的「拍脑袋限流」；**永久静音** 关键告警。  
- **实践**：跨服务 trace 解读；极简容量/压测结论表；可选做一次 **告警规则评审**（删/并/改阈值）。  
- **阅读**：SkyWalking、Micrometer、Prometheus；云 APM **采样与成本**；Google SRE **告警相关章节**（撰写时检索）。

### 阶段 6：云原生交付与架构师职能综合

- **决策焦点**：上线 **回滚与演练**；安全与合规 **残余风险** 谁签字。  
- **主题**：镜像分层、JVM 容器参数、探针、优雅下线；K8s 滚动与会话；密钥；SLI/SLO、评审清单。  
- **反模式**：探针错配导致误杀；镜像无分层构建拖垮交付。  
- **实践**：ADR + 模拟评审；YAML/Helm **最小可读**。  
- **阅读**：K8s、OCI、云容器与审计文档；等保/Well-Architected（按需）。  
- **软技能提示**：架构师需要具备良好的 **沟通、谈判与推动** 能力，能够在不同利益相关方之间达成共识。

## 从基础到进阶（一行版）

**1–2**：故障模型 + **DDD 与契约** → **3–4**：韧性 + 数据一致性的 **模式化决策** → **5–6**：观测容量闭环 + **交付治理与 ADR**。

## 学习方法提示

- 做 **对比实验** 而非演示实验：对比「有治理 vs 无治理」「模式 A vs 模式 B」在 **同一故障注入** 下的表现差异。  
- 建立 **故障案例库**：每掌握一个模式，收集 **3 条** 真实生产故障案例（诱因、扩大因子、止血方式），对照本路线的场景簇自检。  
- 写 **ADR**：每一次有意义的技术决策，用 ADR 记录 **备选方案、选中理由、残余风险**（可与阶段 6 评审清单合并养成习惯）。

## 常见学习误区

- **技术选型焦虑**：容易在「最新栈 vs 保守栈」上空转；本路线主张 **先约束与语义**，往往 **最简单且可运维** 的方案最合适——复杂栈要有 **可辩护的增量价值**。  
- **追求「完美架构」**：不存在一劳永逸；只有 **当前阶段** 在一致/成本/组织成熟度下的 **最合适**。接受 **残余风险** 并写入 ADR。  
- **忽视「人的因素」**：边界、契约、评审、值班与 **组织耦合**；架构失败经常是 **协作与激励** 问题，而非单纯技术错误。  
- **只学不练**：模式必须经 **对比实验、故障推演或真实项目切片** 验证；否则停留在术语层。
