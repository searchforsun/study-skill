## 一、缓存模式与三大经典问题：穿透、击穿、雪崩

缓存提升性能的方式很简单：把"算得慢"或"离得远"的数据放到更近、更快的地方。但脆弱的缓存一旦失效，请求会直接穿透到数据库——这引入了三个经典问题：**穿透**（查不存在的数据）、**击穿**（热点 key 过期）、**雪崩**（大量 key 同时过期或缓存层宕机）。三者的共同根源是**缓存与数据库之间缺少防御性降级层**——如果把缓存当成"加速器"而非"保护罩"，任何一个环节破裂都会直达数据库。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | 缓存穿透 | 查数据库中也不存在的数据 → 缓存永远不生效 → 布隆过滤器 + 空值缓存拦截 |
| 2 | 缓存击穿 | 热点 key 过期瞬间大量并发穿透 → 分布式互斥锁或逻辑过期 |
| 3 | 缓存雪崩 | 大量 key 同时过期 或 缓存层宕机 → 随机 TTL + 多级缓存 + 熔断降级 |
| 4 | Cache-aside 模式 | 读：先缓存后库 → 未命中则查库写缓存；写：先库后删缓存；**先删缓存还是后删取决于并发风险** |

### 1.1 穿透：防御不存在的数据

**缓存穿透的本质是：攻击者或异常逻辑不断查询数据库中也不存在的数据，缓存层形同虚设。** 因为查不到数据 → 写不进缓存 → 每次都打数据库。在高 QPS 下数据库连接池被这种"无效查询"占满，正常请求反而进不去。

防御分两层：第一层是**前置拦截**——用布隆过滤器（Bloom Filter）判断一个 key **是否可能存在**。布隆过滤器用多个哈希函数映射到位数组，查询时全为 1 才算"可能存在"，有一个 0 就是"绝对不存在"。它的工程优势是空间效率极高（1 亿个 key 约 120MB），代价是有**假阳性**（告诉你"可能存在"，实际不存在，概率可控但不可消除）。第二层是**兜底空值缓存**——布隆漏过来的请求，如果数据库也查不到，就在缓存中写一条**短 TTL（30~120s）的空值标记**，下次同样的恶意 key 不会再次穿透。

布隆过滤器的维护成本不可忽视：新增数据时需要同步更新布隆，否则合法 key 可能被误拦。因此它适用于 key 空间稳定或变更可控制的场景（如用户 ID、商品 ID），不适合 key 频繁动态生成的场景（如随机 token）。

### 1.2 击穿：热点 key 过期的瞬间放大

**击穿的破坏力来自并发放大效应**：一个热点 key 过期瞬间，可能有数百个线程同时发现缓存未命中、同时去数据库查询同一条数据。数据库的这 N 次查询——在缓存存活时本来只会有 1 次——让原本也许能扛住 QPS 的库瞬间过载。

击穿的本质是**重建缓存的并发控制缺失**。解决方案——分布式互斥锁——听起来简单但有几个容易翻车的细节：

- **必须双重检查**：拿到锁后再次查缓存（因为在你等锁的过程中，前一个线程可能已经重建完毕）。
- **必须防锁误删**：释放锁时校验锁持有者身份——用 `UUID` 或线程标识作为锁的 value，删除前比较。否则线程 A 的锁过期被线程 B 拿到，A 执行完毕删了 B 的锁。
- **锁的过期时间不能拍脑袋**：设置太长 → 线程 panic 后锁长时间不释放；太短 → 重建未完成锁已释放。Redisson 的 `watchdog` 自动续期是更稳健的选择，但要理解其代价（需要 Redis 连接保活）。

**逻辑过期**（永不过期 + 异步刷新）是另一个方向：物理上不设 TTL，在 value 中嵌入一个逻辑过期时间戳。查询线程发现逻辑已过期时，先返回旧值保证响应速度，然后尝试获取锁、异步重建。这牺牲了一致性（返回旧数据）换取零等待——适合对实时性要求不高的热点数据（如首页推荐、排行榜）。

### 1.3 雪崩：系统性崩塌的三种诱因

**雪崩不是单个 key 的问题，而是一组 key 或整个缓存层的问题。** 三种典型诱因：

1. **大量 key 同时过期**：缓存预热时批量写入，TTL 都相同 → 同时过期 → 流量洪峰同时打到数据库。解法很简单：在基础 TTL 上叠加 ±10%~30% 的随机偏移——让过期时间离散化。
2. **缓存服务宕机或集群分片不可用**：单点 Redis 挂掉后所有请求穿透——这要求缓存层本身必须是高可用（哨兵/集群），同时**业务侧有熔断降级**：检测到 Redis 不可用后，返回静态降级数据或限流，而不是硬扛到数据库。
3. **重建操作引发的二次雪崩**：缓存失效后，大量请求去数据库重建，而重建本身开销很大（复杂 SQL JOIN），导致数据库更慢、更多请求超时 → 恶性循环。**预热 + 多级缓存（Caffeine 本地 → Redis 分布式）** 是有效的防雪崩手段：本地缓存 TTL 短但重建轻量，即使 Redis 全挂，本地缓存也能扛住一部分请求。

### 1.4 Cache-aside 与写一致性

**缓存模式中最常用的是 Cache-aside**：读的时候先去缓存，未命中则查库、写缓存、返回；写的时候**更新数据库 → 删除/更新缓存**。关键问题在于"先删缓存还是后删"——正确顺序是**先更新数据库，再删除缓存**：如果反过来，删缓存→别线程读未命中→查旧库数据→写旧数据到缓存→本线程更新数据库，缓存中留下的是旧数据，直到下次失效。而"先库后删"的并发风险是：线程 A 查库得旧值（未写缓存）→线程 B 更新库删缓存→线程 A 继续把旧值写进缓存。这个窗口极小（要求 B 的写库在 A 的读库和写缓存之间完成），发生概率远低于"先删后库"的在线程交错中保留脏数据。

**该不该用更新替代删除？** 对于并发读多写少、对短暂不一致容忍度极低的场景，可以更新而非删除——但更新面临并发写覆盖的问题，且缓存中保存的数据版本需要能对应。一般原则：**默认删缓存**，只在写后立刻有大量读且延迟敏感的极端场景下才用更新。

## 二、读写分离与读一致性：延迟窗口内的业务语义选择

读写分离是数据库扩展读能力的最经济手段——加从库比垂直升级主库便宜得多。但异步复制引入了**主从延迟**：从库的数据是主库几毫秒到几秒前的快照。问题不是延迟本身，而是**业务代码是否意识到了这种延迟**——当你允许一个刚写入的用户去从库查询自己刚刚提交的数据、结果查不到时，用户投诉的不是"主从延迟"，而是"数据丢了"。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | 主从延迟的本质 | binlog → relay log 的异步复制链路；IO 线程拉取与 SQL 线程回放不是实时的 |
| 2 | 读一致性分级 | 强一致/会话一致/最终一致；三级对应三种**业务语义**而非三种技术方案 |
| 3 | 选择性读主 | 对刚写入的 key 在短 TTL 缓存中标记，命中则强制读主——精确且低成本 |
| 4 | 从库延迟超阈值的处理 | 拒绝读从/降级读主/告警；阈值应按 P99 而非平均值设定 |

### 2.1 读一致性的三级业务语义

**不要用技术方案反推业务可接受什么——而要从业务语义出发，逐级提问。**

**强一致性（读主或全局一致代理）**：适用于"写完后立即查、查不到就是 Bug"的场景。典型如：支付成功后跳转结果页——用户付了钱但页面显示未支付，客服电话量会飙升。实现上可直接 `FORCE_MASTER` hint 读主，或用云厂商的全局一致性代理（如 PolarDB 的全局一致性模式，基于 LSN 确保只读节点返回的版本不早于主库已提交版本）。

**会话一致性**：适用于"同一用户/同一会话内读写连续，跨会话无所谓"的场景。用户修改了个人信息后立即看到新值——但另一个用户看到的是旧值可以接受。实现上用缓存（如 Redis，TTL 设置为可能的最大延迟窗口，通常 3~10 秒）记录"此 key 刚被写过"，该会话内的读请求若命中此标记则读主。这是性价比最高的方案。

**最终一致性**：适用于"晚几秒看到无所谓"的场景——搜索结果、推荐列表、历史记录、统计报表。直接读从库即可，延迟窗口内的不一致是已知且可接受的残余风险。

**关键不是选哪一级，而是把"选的哪一级"写进 ADR（架构决策记录）**——让所有人清楚"这个读操作在读从，可能有 N 秒的延迟窗口"——而不是默默依赖默认行为最后被故障暴露。

### 2.2 选择性读主：精准且低成本

**不是所有读都要读主——只有"刚写过的 key"才需要。** 核心思路：写入完成后，在 Redis 中设置 `db:table:pk` 为 key，TTL = `max_replication_lag(99 分位) + buffer(1~2s)`。读请求先查这个缓存，命中 → 读主；未命中 → 读从。TTL 过期后自动回到读从——相当于把一致性的"紧急性"压缩到了一个短暂的窗口。

这个方案的优雅之处在于：它把一致性负担从"每个读都判断"降为"只对近期变更的数据做判断"，并且 TTL 自动管理过期清理。代价是增加了一次 Redis 查——但这 1ms 的额外开销远低于把所有读都打到主库的成本。

### 2.3 ProxySQL 中间件控制

如果使用了 ProxySQL 这类数据库代理，SQL 级别的路由规则可以实现**对业务代码零侵入**的读写分离：

- `SELECT ... FOR UPDATE` → 自动路由到主库（因为有写意图）。
- 普通 `SELECT` → 路由到从库池，按权重分发。
- `max_replication_lag` 参数 → 从库延迟超过阈值自动从路由池中踢出。

但中间件路由也有盲区：它看不懂**业务语义**——如果业务需要"刚才写的那条必须在结果里"，中间件不知道"刚才"是什么意思。因此**中间件路由 + 业务侧的 selective-read-master 标记**是互补关系，不是替代关系。

## 三、分布式事务模式矩阵与选型决策

分布式事务是架构领域被讨论最多、踩坑也最多的主题之一。核心矛盾是：**业务直觉想要 ACID 的简单——一个操作要么全成功要么全失败；但分布式系统的基础设施从设计上就不承诺 ACID**。本章不是教你怎么配 Seata 的参数，而是让你在评审时能画出每种模式的**代价轮廓**，并给出选型的**否决理由**。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | 2PC / XA | 强一致但全局锁阻塞，低并发场景专属；高并发下是性能杀手 |
| 2 | TCC（Try-Confirm-Cancel） | 业务层两阶段——Try 预留资源，Confirm 提交，Cancel 释放；开发代价极高 |
| 3 | Saga | 长事务拆成串行子事务 + 逆序补偿；编排式 vs 协同式各有 trade-off |
| 4 | Outbox / 本地消息表 | 在同一 DB 事务中写业务数据 + 消息表，异步投递 MQ；中小团队最低成本起点 |
| 5 | 最大努力通知 | 定时间隔重试通知直到确认或超时；非核心链路适用 |

### 3.1 2PC / XA：全局锁的代价

**XA 协议是唯一能提供跨库 ACID 保证的方案，但代价是全局锁。** 协调者向各参与者发 Prepare，所有参与者把事务状态写入本地日志并持有行锁，等协调者发 Commit 才释放。如果协调者在 Commit 阶段宕机，参与者持有的锁不会自动释放——这就是 XA 的**阻塞问题**：锁的持有时间 = 参与者处理时间 + 协调者处理时间 + 网络 RTT × 2 + 可能的协调者恢复时间。在高并发下，这个窗口足以引发连锁锁等待和连接池耗尽。

适用边界很窄：**低并发、多数据源必须强一致、短事务**——例如金融核心账本系统（冲正操作）、监管要求的跨库原子操作。凡超出此边界，先用 Saga 或 Outbox 降低一致性要求。

### 3.2 TCC：把两阶段从数据库搬到业务层

**TCC 的核心思路是把 XA 的数据库层 Prepare/Commit 翻译成业务层的 Try/Confirm/Cancel。** Try 阶段对资源做"预留"（如冻结库存而非扣减），Confirm 把预留转实际消耗，Cancel 把预留释放。每个参与服务都必须实现这三套逻辑——并且必须保证幂等（Confirm/Cancel 可能被重复调用）和**空回滚**处理（协调者发了 Cancel 但 Try 根本没执行到——比如网络异常导致 Try 请求未送达但 Cancel 先到了）。

TCC 的开发成本在所有方案中最高：每个业务接口 × 3 套实现 × 幂等 × 空回滚 × 防悬挂。因此它只适用于**高并发、短事务、必须接近实时一致**的核心链路——典型如电商秒杀的库存扣减、支付系统的账户转账。凡超出此边界的场景，TCC 的代码侵入性带来的维护负担往往超过它提供的一致性价值。

### 3.3 Saga：长事务的补偿思维

**Saga 不锁资源，每个子事务独立提交，失败时逆序执行补偿操作。** 与 TCC 的区别在于：Saga 的中间状态对外可见（子事务已提交），TCC 在 Try 阶段资源仅预留、对外不可见。这意味着 Saga 的补偿是事后修正——如果 CancelBooking 补偿失败，需要人工介入或进入死信队列。因此 Saga 适合**长流程、异步、允许中间状态**的场景：如订单全流程（创建 → 支付确认 → 发货 → 签收），每步独立提交，任一步失败逆序补偿（退款 → 取消发货）。

编排式（Orchestration）比协同式（Choreography）更适合生产：状态机集中管理 Saga 流转，避免"每个服务各自发事件、谁都不知道全局到哪步"的混乱。Seata Saga 的事务状态机 DSL 是当前国内生态中最成熟的实现。

### 3.4 Outbox：低成本起步的最优解

**Outbox（本地消息表）是分布式事务家族中最不"分布式"的方案——它几乎不增加架构复杂度。** 核心操作被压缩在**一个本地数据库事务**中：

```mermaid
sequenceDiagram
    participant Biz as 业务服务
    participant DB as 业务DB（含outbox表）
    participant Poll as 定时任务
    participant MQ as 消息队列
    participant Consumer as 下游消费者

    Biz->>DB: BEGIN; INSERT 订单 + INSERT outbox(消息); COMMIT
    Poll->>DB: SELECT 未投递消息 LIMIT N
    Poll->>MQ: 发送消息
    MQ-->>Poll: 确认
    Poll->>DB: UPDATE outbox SET status='SENT'
    MQ->>Consumer: 推送消息
    Consumer->>Consumer: 幂等处理
```

关键设计点：
- **消息表与业务表在同一数据库、同一事务**——利用 ACID 保证"业务数据落盘 = 消息一定在表里"，不需要分布式协调。
- **定时任务轮询**：间隔 1~5 秒拉取 `status=PENDING` 的记录投递到 MQ，投递成功后标记为 `SENT`。幂等投递：如果 MQ 已经收到但标记未来得及更新，下次轮询重投——消费端必须幂等。
- **消息体设计**：包含**聚合类型 + 事件类型 + 聚合 ID + 时间戳 + 业务 payload**——以便消费端做路由和去重。

Outbox 适合 **80% 的异步解耦场景**：下单后发积分/优惠券、状态变更通知下游、非核心链路的跨服务同步。它的延迟是定时轮询间隔（秒级），不适合要求毫秒级/秒级实时一致的场景——此时需要升级为 **CDC（Change Data Capture）+ 实时投递**（如 Debezium 监听 binlog 直接写入 Kafka），消除轮询延迟。

### 3.5 选型决策框架

**第一步不是选方案，而是确定业务到底要什么一致性级别：**

```
业务场景分析
├─ 必须强一致（零容忍）？
│   ├─ 低并发（TPS < 100）→ 2PC / XA
│   ├─ 高并发（TPS > 1000）→ 审视：能否重构为预冻结+对账 → TCC
│   └─ 跨多个步骤(>3步、>1s) → 审视：能否拆为多个最终一致的本地事务 → Saga
├─ 可接受最终一致（秒级）？
│   ├─ 高并发短事务（<1s）→ TCC
│   ├─ 长流程（>5步、>5s）→ Saga（编排式优先）
│   │   └─ 实时性要求更高 → Saga + 事件驱动（CDC 消除轮询延迟）
│   └─ 简单异步解耦 → Outbox / 本地消息表
└─ 可接受最终一致（分钟级）？
    ├─ 需要可靠通知 → Outbox + MQ + 消费端幂等
    └─ 非核心，丢了也能接受 → 最大努力通知
```

**否决理由写进 ADR 的模板**：_"本场景需要强一致，但 TPS 峰值 5000，否决 2PC/XA——全局锁阻塞窗口不可接受。选择 TCC，残余风险为：Confirm/Cancel 幂等实现错误导致数据不一致，缓解措施为每日对账 + TCC 事务日志告警。"_

## 四、消息语义与跨聚合协作

从阶段 2 的 DDD 视角看，消息是**限界上下文之间的通信合约**——不是"顺便发个 MQ"。跨聚合的协作不应通过"一个事务同时修改两个聚合"来实现（那会破坏聚合的独立性），而应通过**领域事件**：聚合 A 在自己的事务边界内完成状态变更 + 发布领域事件，聚合 B 订阅该事件并做自己的处理。这个模型的核心要求是：**事件发布与聚合状态变更必须是原子操作**——这正是上一章 Outbox 模式要解决的问题。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | 领域事件 | 聚合内部状态变更的副产物，不是技术通知——事件名使用业务语言 |
| 2 | 跨聚合协作 | 通过事件驱动而非分布式事务——聚合 A 和 B 各自在自己的事务中保持一致 |
| 3 | 事件至少一次投递 | 消费者必须基于事件 ID + 聚合 ID 做业务幂等 |
| 4 | 事件顺序 | 同聚合的事件顺序有意义（版本号/时间戳可验证）；跨聚合的事件天然无序 |

### 4.1 为什么跨聚合不应用分布式事务

**如果你在同一个分布式事务中修改了订单聚合和库存聚合，这两个聚合就不是独立的——它们被事务边界耦合成一个"分布式聚合"。** DDD 聚合设计的初衷是每个聚合有自己的不变式（invariant），在聚合内部用本地 ACID 事务保护。跨聚合的"业务一致性"应该是**最终一致的**：订单已创建 → 库存扣减 → 如果库存扣减失败 → 订单标记为库存不足并退款——这是一个**业务流程**，不是一个**数据库事务**。

用 Sagas/事件 替代跨聚合大事务的本质是：**把技术层的分布式事务，转化为业务层的补偿流程**——让业务规则（而非数据库锁）来保证最终一致。

### 4.2 事件设计的四条约束

1. **事件名用业务语言**：`OrderPaid` 而非 `OrderStatusChanged`——前者表达了业务意图，后者只是状态变化信号。
2. **事件携带足够的路由和去重信息**：`{ eventId, aggregateType, aggregateId, eventType, occurredAt, payload }`。
3. **同聚合的事件携带版本号**：消费端可以校验 `aggregateVersion == expectedVersion + 1` —— 发现跳版本意味着丢事件，需要补偿。
4. **消费端去重**：以 `eventId` 或 `aggregateId + aggregateVersion` 为唯一键——不是"建议"，是至少一次投递下的必须。

### 4.3 CDC 加速：从轮询到实时

当业务要求跨聚合的最终一致延迟从"秒级"缩短到"毫秒级"时，传统的定时轮询 Outbox 表不再适用。**CDC（Change Data Capture）** 监听数据库 binlog，Outbox 表有 INSERT 时立即捕获并投递到 MQ——把轮询间隔从 1~5 秒降到近乎实时。Debezium + Kafka 是这个模式在国内最常用的技术组合。

但 CDC 引入新的运维复杂度：Debezium 需要维护 binlog 消费位点、处理 DDL 变更、容灾切换时的位点对齐。**只在真正需要毫秒级事件延迟时才引入 CDC**——对于大多数业务场景，1~5 秒的轮询延迟完全在可接受范围。

---

**本节提要（延伸学习）**

- **核心概念**：领域事件（业务语言命名）、跨聚合最终一致（非分布式事务）、事件版本号与跳版本检测、CDC 实时投递（Debezium + binlog）、消费端 eventId 去重
- **拓展提问提示词**

> 主题：基于领域事件的跨聚合协作与消息投递语义。核心概念：聚合不变式与本地事务边界、领域事件 vs 技术通知、事件携带 aggregateId + aggregateVersion + eventId、Outbox → CDC 的延迟演进路径、消费端幂等去重键设计。请拓展：事件溯源（Event Sourcing）与 Outbox 的组合应用；Schema Registry 对事件版本演进的支持（Avro/Protobuf）；"至少一次投递"下的业务补偿与对账模式；多个聚合各自发布事件时因果一致性的保证与局限。产出格式：事件设计清单 + CDC 架构图 + 幂等键选择决策树。

## 五、分库分表：决策清单与反模式

分库分表是 Java 分布式架构中最容易出现"过度设计"的领域之一。过早拆分带来的运维税——跨库查询、分布式事务诱惑、扩容再均衡——往往远超数据量本身带来的压力。在考虑分库分表之前，必须先用尽所有更便宜的方案。

| # | 知识点 | 抓住什么 |
|---|--------|----------|
| 1 | 决策前置条件 | 分库分表前先问：垂直拆分做了吗？归档做了吗？读写分离做了吗？ |
| 2 | 分键（Sharding Key） | 决定数据分布的均匀性与查询路由——分键选错，后续代价是指数级 |
| 3 | 扩容与再均衡 | 一致性哈希 vs 分片再均衡；双写 + 灰度切流是生产唯一安全路径 |
| 4 | 反模式 | 为分而分、分键与领域边界不对齐、分库后忍不住上分布式事务 |

### 5.1 先问四个问题再决定分不分

决策顺序应该是：

1. **垂直拆分做了吗？** 把不同业务域的表放到不同数据库——这是领域边界对齐的操作，不涉及任何分布式事务复杂性，是目前性价比最高的拆分。
2. **冷热分离做了吗？** 历史数据归档到离线存储——热表数据量下降后，单表性能足以应对。
3. **读写分离做了吗？** 读压力远大于写压力时，加只读从库是比分库分表更便宜的方案。
4. **单表数据量真的撑不住了吗？** MySQL 单表 5000 万行以内 + 合适索引，通常不需要分表——瓶颈往往在 SQL 质量或索引设计，而不在表大小。只有确认前三步都不够、且 SQL/索引优化已到极限后，才启动分库分表。

**如果前三步没做完就分库分表，你是在用最贵的方案解决能用便宜方案解决的问题。** 而且分库分表后，前三步中的部分手段（如垂直拆分）可能变得更为困难——跨库 JOIN 变成了应用层聚合，事务边界变得模糊。

### 5.2 分键是分库分表的第一性决策

**分键（Sharding Key）一旦选定，几乎无法低成本变更。** 它决定了：

- **数据分布的均匀性**：分键的基数需要足够大（如 userId、orderId），避免热点分片。
- **查询路由的有效性**：绝大多数查询必须携带分键才能定位到正确的分片——否则需要全分片扫描。
- **与领域边界的对齐**：分键应匹配领域聚合的根 ID —— 如果订单聚合以 `orderId` 为根，则分键也应为 `orderId`，而不是 `userId`（尽管用户维度的查询很常见——但那是另一个问题，可以通过异构索引表或 ES 解决）。

**分键错误的最常见表现**：选了一个"看起来通用"的键（如商户 ID），但大量查询并不携带它——导致每次查询都要扫全分片；或分键基数太低（如状态值），导致数据严重倾斜（90% 的数据在 1 个分片上）。分键选错后的修复成本通常意味着**全量数据迁移**——没有在线平滑修改的方案。

### 5.3 扩容：最危险的运维操作

**分库分表后的扩容本质上是一次全量数据重分布。** 一致性哈希（如 ShardingSphere 的 `HASH_MOD`）可以让新增节点只迁移一部分数据而非全量，但迁移过程本身——数据在分片间移动时的读写一致性保证——是极高风险的操作。

生产环境唯一的扩容安全路径是**双写 + 灰度**：

1. 新路由规则写入配置中心。
2. 双写阶段：同时写入旧分片和新分片（按新规则计算目标），读取仍走旧。
3. 历史数据迁移：后台任务按新分片规则将存量数据迁移到新分片。
4. 灰度读切换：小比例流量读新分片，校验数据一致性。
5. 全量切读 + 停止双写旧分片。

这个流程通常持续数天到数周，需要完整的监控、对账、回滚预案。**分库分表不是一劳永逸的——它引入了终身的扩容焦虑。**

### 5.4 反模式速查

| 反模式 | 为什么错 | 正确做法 |
|--------|---------|----------|
| **为分而分** | 单表 100 万行就担心性能——实际上 5000 万内索引合理完全够 | 先优化 SQL 和索引 |
| **分键选错** | 选了不带在查询条件里的字段 → 全分片扫描 | 选聚合根 ID，确保 90%+ 查询携带 |
| **分库后上分布式事务** | 用分布式事务掩盖分库带来的事务边界变化——跨分片事务本就不该存在 | 重构聚合边界，确保一个聚合在一个分片内 |
| **不分库只分表** | 分表不分库——把热点都留在同一个物理实例上 | 分库的本质是隔离压力，需要两者配合 |
| **忽略应用层聚合成本** | 原本一个 SQL 能做的事，现在要 N 次查询 + 应用层聚合 | 评估时把应用层代码复杂度也计入成本 |

**本节提要（延伸学习）**

- **核心概念**：分键（Sharding Key）的第一性决策、决策前置四问（垂直拆分→归档→读写分离→再谈分库）、一致性哈希 vs 范围分片、扩容的双写+灰度安全路径、分键错误的数据倾斜、聚合应与分片对齐
- **拓展提问提示词**

> 主题：分库分表的决策清单、技术约束与防过度设计。核心概念：分库前的降级替代方案（垂直拆分/归档/读写分离）、分键选择的三条原则（高基数/查询覆盖/领域对齐）、一致性哈希 vs 取模的扩容对比、双写+灰度切流的扩容流程、分库后跨分片查询（异构索引/ES 冗余）的辅助方案、分库分表中间件（ShardingSphere/Mycat/Vitess）的选型要点。请拓展：分片键选错后的在线修正方案与风险；分库后索引设计的变化（本地索引 vs 全局索引）；分布式 ID 生成策略（雪花算法/号段/DB 自增）的分库兼容性对比；分库分表后的运维脚本（数据校验/对账/重分布）最低要求。产出格式：决策前置检查清单 + 扩容时间线 + 反模式案例集。
